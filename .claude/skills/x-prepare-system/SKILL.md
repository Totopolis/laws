# Подготовка системы поиска по кодексам

Скилл приводит репозиторий в состояние «поиск работает»: ставит зависимости, качает модель
и **проверяет всю цепочку целиком** — от импорта библиотек до вызова MCP-инструмента
по протоколу. Вся механика в `src/laws_mcp/setup_check.py`; задача скилла — запустить её
с нужными флагами, правильно понять, что именно не сошлось, и не начать чинить лишнее.

Скилл работает в репозитории с кодексами и ничего в нём не удаляет: только ставит
зависимости, качает модели и проверяет.

## Что должно быть на машине

| Что | Размер | Откуда берётся |
|---|---|---|
| `.venv/` с рантайм-зависимостями | ~200 МБ | этот скилл |
| `models/qwen3-emb-onnx/` — эмбеддер fp32 | 2,3 ГБ | этот скилл (Hugging Face) |
| `models/bge-reranker-onnx/` — реранкер int8 | 544 МБ | этот скилл (необязателен) |
| `data/` — тексты кодексов по статьям | 80 МБ | уже в репозитории |
| `index/` — векторный индекс | 68 МБ | уже в репозитории |

Модели в репозиторий не входят (`models/` в `.gitignore`) — их качает этот скилл.
Тексты и индекс, наоборот, поставляются готовыми: пересчитывать их здесь нечем и незачем.
Видеокарта не нужна — поиск считается на процессоре.

## Шаг 1 — окружение

Проверь, что venv есть и это именно он:

```bash
ls .venv/Scripts/python.exe    # Windows
```

Если venv нет — создай (нужен Python 3.11+):

```bash
python -m venv .venv
```

Дальше **все команды — через `.venv/Scripts/python.exe`**, не через системный python.

## Шаг 2 — проверить, что уже есть

Сначала прогон без установки: он ничего не меняет и показывает полную картину.

```bash
PYTHONPATH=src PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe -m laws_mcp.setup_check
```

Проверки идут по порядку зависимости, и первые три — блокирующие: если не сошлись
зависимости, модель или данные, остальное не запускается, потому что бессмысленно.
Читай **первую** строку `[нет]`, а не последнюю: она и есть причина.

## Шаг 3 — доустановить недостающее

```bash
PYTHONPATH=src PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe -m laws_mcp.setup_check --install
```

Ставит рантайм-библиотеки и качает модель (~2,3 ГБ) вместе с реранкером (544 МБ).
Это надолго — таймаут от 30 минут. Видеокарта не нужна: поиск считается на процессоре.

Модель эмбеддера нужна именно **fp32**. Не подменяй её на int8 ради размера: её векторы
не совпадают с индексом (косинус 0,73 вместо 1,0), поиск при этом не падает, а молча выдаёт
ерунду. Скилл проверяет размер каталога и ругается, если модель меньше 2 ГБ.

С реранкером наоборот: он берётся в **int8** и это нормально. Он выдаёт оценку пары
«запрос + статья», а не вектор в общем с индексом пространстве, поэтому совпадать ему
не с чем — качество квантования проверяется метрикой (`evaluate onnx dense dense+rerank`),
и int8 там не уступает fp32. Без реранкера поиск работает, просто хуже на расплывчатых
запросах, поэтому его отсутствие — предупреждение, а не ошибка.

## Шаг 4 — данные

Тексты (`data/`) и индекс (`index/`) приходят вместе с репозиторием, отдельного шага
не требуют. Если проверка говорит, что их нет, — это неполная сборка: пересчитать
их на месте нечем, нужна замена репозитория от поставщика. Ничего не скачивай
и не пытайся строить.

## Шаг 5 — убедиться, что всё работает

Финальный прогон без флагов должен закончиться строкой
**«система готова: модель, индекс, CLI и MCP работают»**. Он проверяет по очереди:

1. импорт рантайм-библиотек;
2. модель на месте и правдоподобного размера;
3. `data/` и `index/` на месте;
4. живой поиск — реальный запрос через модель и индекс;
5. чтение статьи из `data/` по индексу;
6. **контрольные запросы** — recall на восьми эталонных вопросах;
7. CLI отдельным процессом — так же, как его зовёт `/x-search-laws`;
8. пересортировка (если реранкер стоит): ст. 1064 ГК по запросу «сосед залил квартиру»
   должна подняться с 9-го места в первую тройку;
9. MCP-сервер: поднимается как подпроцесс и отвечает на вызов инструмента по протоколу.

После этого можно искать (`/x-search-laws`) или подключить MCP-сервер (`/x-run-mcp`).

Пункт 6 — не формальность: рассогласование модели и индекса не ломает поиск, оно только
портит выдачу, и поймать его можно лишь метрикой. Если recall упал ниже 90% — почти
наверняка скачана не та сборка модели (нужна fp32, а не int8): удали `models/qwen3-emb-onnx`
и повтори с `--install`.

## Отчёт пользователю

Скажи: что было доустановлено и скачано, что найдено в `data/` и `index/`,
результат финального прогона и сколько времени заняло. Если что-то не сошлось — назови
**первую** непройденную проверку и конкретный следующий шаг, а не весь список.

Если чего-то не хватает в самих данных (нет `data/` или `index/`), скажи прямо:
это неполная поставка, и на месте она не чинится.

## Типичные сбои

- **`ModuleNotFoundError` при запуске самого setup_check** — запущен системный python
  или забыт `PYTHONPATH=src`.
- **Модель качается и обрывается** — просто перезапусти с `--install`: уже скачанные
  файлы заново не качаются, докачается остаток.
- **Мало места на диске** — модель 2,3 ГБ и реранкер 0,5 ГБ. Скилл печатает свободное
  место первой строкой.
- **MCP-сервер не отвечает** при исправном CLI — почти всегда несовместимость SDK:
  в `mcp` 2.x класс называется `MCPServer`, в 1.x — `FastMCP`; `server.py` понимает оба,
  но если SDK совсем другой версии, смотри его ошибку в выводе.
